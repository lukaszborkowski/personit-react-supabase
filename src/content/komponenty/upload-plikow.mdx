# Upload plików

Moduł `files` udostępnia inputy do plików: `FileInput`, `MultiFileInput`, `ImageInput` i `MultiImageInput`. Każdy z nich **zwraca tylko ID pliku z bazy**, nie obiekt `File`.

Zasady:

- każdy plik wrzucony do Storage ma swój wiersz w tabeli `files`,
- plik trafia do Storage od razu po wybraniu, a formularz wysyła już tylko ID,
- pliki, które przez **14 dni** nie zostały do niczego przypięte, usuwa cron.

## Użycie

### 1. Input w formularzu

Input działa jak każde inne pole: `value` to ID (albo tablica ID), `onChange` dostaje ID po udanym uploadzie.

```tsx title="modules/books/components/BookForm.tsx"
import { Controller, useForm } from 'react-hook-form'
import { ImageInput, MultiFileInput } from '@/modules/files'

const bookSchema = z.object({
  title: z.string().trim().min(1, 'Podaj tytuł'),
  coverFileId: z.string().uuid().nullable(),
  attachmentIds: z.array(z.string().uuid()),
})

export function BookForm({ onSubmit }: BookFormProps) {
  const form = useForm<BookValues>({
    resolver: zodResolver(bookSchema),
    defaultValues: { title: '', coverFileId: null, attachmentIds: [] },
  })

  return (
    <form onSubmit={form.handleSubmit(onSubmit)} className="space-y-4">
      {/* … */}
      <Controller
        control={form.control}
        name="coverFileId"
        render={({ field }) => <ImageInput value={field.value} onChange={field.onChange} />}
      />
      <Controller
        control={form.control}
        name="attachmentIds"
        render={({ field }) => <MultiFileInput value={field.value} onChange={field.onChange} />}
      />
    </form>
  )
}
```

Dostępne inputy:

| Komponent | `value` | Do czego |
| --- | --- | --- |
| `FileInput` | `string \| null` | jeden dowolny plik |
| `MultiFileInput` | `string[]` | lista plików |
| `ImageInput` | `string \| null` | jeden obraz z podglądem |
| `MultiImageInput` | `string[]` | galeria obrazów |

### 2. Zapis formularza

Do bazy idą zwykłe kolumny z ID. Nie ma tu żadnego `FormData` ani uploadu – pliki są już w Storage.

```ts title="modules/books/api/books.api.ts"
export async function createBook(shelfId: string, input: BookInput): Promise<Book> {
  const { data, error } = await supabase
    .from('books')
    .insert({ shelf_id: shelfId, title: input.title, cover_file_id: input.coverFileId })
    .select(BOOK_COLUMNS)
    .single()
  if (error) throw error

  if (input.attachmentIds.length) {
    const { error: attachError } = await supabase
      .from('book_attachments')
      .insert(input.attachmentIds.map((fileId) => ({ book_id: data.id, file_id: fileId })))
    if (attachError) throw attachError
  }

  return toBook(data)
}
```

### 3. Podgląd pliku po ID

Kiedy mamy tylko ID (np. okładka w liście książek), URL pobieramy hookiem z modułu:

```tsx
const { data: cover } = useFile(book.coverFileId)

<img src={cover?.url} alt={book.title} />
```

## Jak to działa

```text
wybór pliku ──▶ insert do `files` ──▶ upload do Storage ──▶ input zwraca ID
                                                              │
submit formularza (tylko ID) ──▶ rekord wskazuje na plik ──▶ trigger: attached_at = now()
                                                              │
cron raz dziennie ──▶ pliki z attached_at = null starsze niż 14 dni ──▶ usuń z Storage i z `files`
```

### Tabela `files`

```sql title="supabase/migrations/…_files.sql"
create table public.files (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  mime_type text not null,
  size bigint not null,
  owner_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  -- null = plik nieprzypięty do żadnego rekordu, kandydat do sprzątania
  attached_at timestamptz,
  created_at timestamptz not null default now()
);

create index files_orphans_idx on public.files (created_at) where attached_at is null;
```

Plik w Storage leży pod ścieżką `{owner_id}/{id}`. Dzięki temu polityka Storage sprawdza tylko pierwszy folder, a z wiersza w `files` zawsze wiemy, gdzie jest plik.

### Upload

```ts title="modules/files/api/files.api.ts"
export async function uploadFile(file: File): Promise<FileRecord> {
  const { data, error } = await supabase
    .from('files')
    .insert({ name: file.name, mime_type: file.type, size: file.size })
    .select(FILE_COLUMNS)
    .single()
  if (error) throw error

  const record = toFileRecord(data)
  const { error: uploadError } = await supabase.storage.from('files').upload(record.path, file)
  if (uploadError) throw uploadError

  return record
}
```

Najpierw wiersz, potem plik. Jeśli upload się nie uda, zostaje wiersz bez przypięcia – cron go posprząta, nie trzeba ręcznie wycofywać.

### Przypinanie

Jedna funkcja triggera dla wszystkich tabel, które wskazują na pliki. W argumencie podajemy nazwę kolumny z ID pliku.

```sql
create function public.sync_file_attachment() returns trigger
language plpgsql security definer set search_path = '' as $$
declare
  col text := tg_argv[0];
  new_id uuid;
  old_id uuid;
begin
  if tg_op <> 'DELETE' then new_id := (to_jsonb(new) ->> col)::uuid; end if;
  if tg_op <> 'INSERT' then old_id := (to_jsonb(old) ->> col)::uuid; end if;

  if old_id is distinct from new_id then
    -- Stary plik (podmieniony albo usunięty rekord) wraca do puli sprzątania
    update public.files set attached_at = null where id = old_id;
    update public.files set attached_at = now() where id = new_id;
  end if;

  return null;
end $$;

-- Pojedynczy plik: kolumna w tabeli
create trigger books_cover_file after insert or update of cover_file_id or delete on public.books
  for each row execute function public.sync_file_attachment('cover_file_id');

-- Wiele plików: tabela łącząca
create trigger book_attachments_file after insert or update or delete on public.book_attachments
  for each row execute function public.sync_file_attachment('file_id');
```

Nowa tabela z plikami = kolumna `… references public.files (id)` + jeden trigger. Ani frontend, ani cron nie muszą o niej wiedzieć.

### Sprzątanie

Plików ze Storage nie usuwamy SQL-em, tylko przez API Storage, więc cron (`pg_cron`) raz dziennie woła Edge Function:

```ts title="supabase/functions/cleanup-files/index.ts"
const ORPHAN_TTL_DAYS = 14

Deno.serve(async () => {
  const supabase = createClient(Deno.env.get('SUPABASE_URL')!, Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!)
  const cutoff = new Date(Date.now() - ORPHAN_TTL_DAYS * 24 * 60 * 60 * 1000).toISOString()

  const { data: orphans, error } = await supabase
    .from('files')
    .select('id, owner_id')
    .is('attached_at', null)
    .lt('created_at', cutoff)
    .limit(1000)
  if (error) throw error
  if (!orphans.length) return Response.json({ removed: 0 })

  const { error: storageError } = await supabase.storage
    .from('files')
    .remove(orphans.map((file) => `${file.owner_id}/${file.id}`))
  if (storageError) throw storageError

  await supabase.from('files').delete().in('id', orphans.map((file) => file.id))
  return Response.json({ removed: orphans.length })
})
```

<Callout type="tip" title="Dlaczego 14 dni">
Margines na formularze otwarte długo albo zapisane jako szkic w przeglądarce. Plik nie znika użytkownikowi spod ręki w trakcie pracy, a śmieci i tak nie zostają na zawsze.
</Callout>

## Jaki problem rozwiązuje

Formularz dodawania książki ma okładkę i załączniki. Rekordu książki **jeszcze nie ma w bazie**. Bez wspólnego mechanizmu są dwa wyjścia i oba są słabe.

**1. Upload od razu po wybraniu pliku, bez rejestru.** Użytkownik wybiera trzy zdjęcia, pliki lądują w Storage, po czym klika „Anuluj” albo zamyka kartę. Pliki zostają w Storage na zawsze i nikt nie wie, które z nich są czyimiś okładkami, a które śmieciami.

```tsx
const onPick = async (file: File) => {
  const path = `${userId}/${crypto.randomUUID()}`
  await supabase.storage.from('files').upload(path, file)
  setCoverPath(path) // discard formularza = osierocony plik
}
```

Ten sam problem przy edycji: użytkownik podmienia okładkę, a stary plik zostaje w Storage.

**2. Formularz razem z plikami w jednym żądaniu.** Śmieci nie powstają przy anulowaniu, ale:

- kilka zdjęć z telefonu potrafi ważyć kilkadziesiąt MB i przekroczyć limit żądania (np. Edge Function),
- submit trwa długo, a użytkownik nie widzi postępu poszczególnych plików,
- błąd jednego pliku albo zerwane połączenie oznacza wysłanie wszystkiego od nowa,
- jeśli pliki weszły do Storage, a insert rekordu się wywalił, i tak mamy śmieci.

**Z modułem `files`** każdy plik wysyła się osobno zaraz po wybraniu (z postępem i błędem per plik), submit formularza to lekki JSON z ID, a wszystko, co nie zostało przypięte – po anulowaniu, zamknięciu karty, podmianie albo nieudanym zapisie – po 14 dniach sprząta cron.

| Sytuacja | Upload bez rejestru | Wszystko w jednym żądaniu | Moduł `files` |
| --- | --- | --- | --- |
| Discard nowego formularza | śmieci w Storage | ok | sprząta cron |
| Podmiana pliku w edycji | śmieci w Storage | śmieci w Storage | sprząta cron |
| Duże / liczne pliki | ok | limit żądania, długi submit | ok, upload per plik |
| Błąd jednego pliku | ok | wszystko od nowa | ponawiamy jeden plik |
| Błąd zapisu rekordu | śmieci w Storage | śmieci w Storage | sprząta cron |

## Props

Wspólne dla wszystkich inputów:

| Prop | Opis |
| --- | --- |
| `value` | ID pliku (`string \| null`) albo tablica ID w wersjach `Multi*` |
| `onChange` | wywoływany z nowym ID / tablicą ID po udanym uploadzie lub usunięciu |
| `accept` | dozwolone typy, np. `'application/pdf'` (w `Image*` domyślnie `'image/*'`) |
| `maxSize` | maksymalny rozmiar jednego pliku w bajtach |
| `maxFiles` | tylko `Multi*` – maksymalna liczba plików |
| `disabled` | blokuje wybór i usuwanie |
